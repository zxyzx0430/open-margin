## 0. 为什么要逐版本迭代

**长期战略（D10 方向 + D13 产品边界确认）：**让用户拥有、掌握并能利用自己的财务数据；A 采集和 B 记录可靠性保持可信底座，C 的价值由**外部 AI 客户端通过清衡 MCP**来实现。清衡当前**不内置 LLM、AI 聊天页、多轮对话模型或模型订阅**。未来若改为闭源上架、订阅制产品，再独立评审是否内置 AI；不得将未来商业化备选方案默认纳入当前开发。

**D12 产品负责人明确认可的功能开发主顺序（方案 A）：**OM-03 采集健康检测 → OM-05 最小 AI 财务分析实验 → OM-02 可开关的成功记账反馈。此处是**功能里程碑的先后顺序**，不是允许跳过现有版本质量门禁的自动排期。

这是产品负责人结合课堂 RICE 做出的**优先顺序选择**，而非 RICE 自己决定的工程顺序。模拟参数和分数仅用于说明模型，不是来自真实用户/人月数据：

| 机会 | Reach（人/月） | Impact | Confidence | Effort（人月） | 模拟 RICE |
| --- | ---: | ---: | ---: | ---: | ---: |
| OM-03 健康检测 | 40 | 2 | 0.8 | 1 | **64** |
| OM-05 AI 最小实验 | 20 | 3 | 0.5 | 0.5 | **60** |
| OM-02 成功提示 | 70 | 0.5 | 0.8 | 0.5 | **56** |

**正式产品排序不能仅凭 RICE。** 数据损坏、误合并、误入账、升级丢账等缺陷属于强制**质量门禁**；不因“得分未上榜”而排到 AI 或成功提示之后。OM-01（重复确认）、OM-04（对账异常）中的完整体验可以分阶段开发，但对核心账目正确性的最小处理必须先通过验收。

### 0.1 方案 A 的决策状态与保护条件

- **已经确认**：产品负责人希望今后**一版一版迭代**，用 **OM-03 → OM-05 → OM-02** 作为功能版本的先后顺序；不为抢某个需求而同时启动三个大版本。
- **推荐但尚待确认**：将 v1.2.0 定位为必须先验收的稳定基线门禁，后续新功能依次用 v1.3.0、v1.4.0、v1.5.0 承载。版本编号为路线草案，不代表发布标签已经存在。
- **质量例外**：若发现真实丢账、误合并、错误入账、同步破坏、危险迁移或签名升级问题，立即成为当前版本的阻断项；不是把 OM-01/04 的所有增强体验提前做完。
- **工程现实**：OM-03 已有部分状态诊断代码，应先核对真实实现和真机表现，而不是把课堂需求当作零起点；OM-05 可用已核对脱敏数据做隔离实验，不暗示线上交易数据已可靠。
- **没有批准**：具体发布日期、人月预算、正式 GitHub Milestone、公开 release、数据库迁移或生产部署，均尚未确认。

### 0.2 当前唯一的启动焦点：v1.2.0 正式验收

**本轮目标一句话：让现有 Android v1.2.0 RC / main 代码安全地变成一个用户敢于升级、能识别真实采集边界的正式基线。**

进入 v1.3.0 新功能开发前，至少拿到下述可追踪证据：

- [ ] 在目标 Android 真机记录 ROM/系统版本、权限与连接状态，明确哪些支付类型能抓取、哪些不能；
- [ ] 同签名原地升级测试，手机历史交易、未同步账目和关键设置保持完整；
- [ ] 同金额真实两笔、通知重放、跨渠道一笔、退款、转账、编辑/删除及离线恢复的对账回归；
- [ ] 后端/客户端最新 CI、隔离备份恢复演练、回滚路径及验收结果链接；
- [ ] 确认实际发布所需的签名、versionCode、服务端兼容与对应 Release 标签；未完成前仅称测试候选。

**触发下一版的条件**：发布门禁通过并记录当前缺陷/遗留风险后，才把 v1.3.0 的 OM-03 需求拆成可开发工单。期间允许做只读研究、设计和隔离原型，但不把研究成果当作已进入正式版本开发。

- 后端、双向同步、OAuth/MCP、Wallos 与合成测试有已记录的可用基线；Android 真机采集、Android 16 厂商 ROM、跨渠道去重正式开启（D05 仍为影子模式）、同证书升级和发布门禁**尚未有完成证据**。

| 里程碑 | 用户能感知的版本承诺 | 主要机会 | 本版核心目标 | 状态 |
| --- | --- | --- | --- | --- |
| **v1.2.0 正式版门禁** | **数据不能在升级/同步/采集时悄悄坏掉** | 现有采集与同步、OM-01 的数据安全底线 | 完成既有 RC6 / 开发基线的真机、升级、回滚和数据正确性验证 | 预发布；未放行 |
| **v1.3.0「看得见」** | **用户知道自动采集有没有真正运行** | **OM-03** | 把已有健康检测补齐为可见、可诊断、能恢复且不骚扰的体验 | 计划草案 |
| **v1.4.0「MCP 可用可信」** | **外部 AI 能经授权 MCP 获得正确、可追溯的清衡数据** | **OM-05 MCP 对外调用验证** | 核对已有 MCP 工具契约，选一个真实财务任务做端到端验收；不开发内置 AI | 计划草案 |
| **v1.5.0「反馈不打扰」** | **用户知道一笔账是否成功保存，又能自主控制提示** | **OM-02** | 轻量成功提示及开关；异常告警独立 | 计划草案 |
| **v1.6.0「异常能闭环」** | **发现、核对并修正异常记录有明确路径** | OM-01 / OM-04 的增强体验 | 集中完善模糊重复确认与待处理流程，不与基础账目修复混淆 | 远期候选 |

> **重要**：以上版本名只是供确认的产品提案；不能把后端历史 `1.5.0` 与本路线 v1.5.0 混为一个版本。前一版本验证未通过，不得通过增加新功能“带病进入下一版”。影响数据正确性的 P0 缺陷无论出现在哪版都优先修复/阻止发布。

### v1.2.0｜正式发布门禁：可信基线

**目标**：当前 RC/开发基线在真实使用环境下可安全升级、可采集其声明支持的交易、可同步且可回滚。

**必须确认**
- Android 16 与目标 ROM 的真机无障碍服务连接、后台/锁屏/重启恢复，记录成功与失败样本；
- 旧版本原签名安装包原地升级，不丢 Room 记录、同步设置和未上传数据；
- 真交易参照账单核对：已完成扣款、退款到账、转入/转出、重复通知、同金额两笔独立交易、重放、离线同步；
- 跨渠道合并与删除/编辑墓碑不产生重复/误合并/旧账复活；**D05 影子规则仅在通过 D01/D06/D07 后考虑开启**；
- 正式备份、恢复演练、回滚路径、对照账本统计和对应 CI 都有留痕；
- 不能观察到的第三方支付事件必须写明覆盖边界，不宣称“100% 自动识别”。

**不做**：AI 财务助手、成功弹窗大改版、复杂待处理中心。发现 P0 账目问题必须作为发布阻断项，不可递延到 v1.6。

**退出标准**：按 [v1.2.0 发布门禁](RELEASE_V1.2.0_CANDIDATE.md) 与 [STABLE_BASELINE.md](STABLE_BASELINE.md) 逐项保留可验证证据，并由负责人确认发布/回滚。

### v1.3.0｜采集健康可见（OM-03）

**核心任务**：用户有理由相信自动采集正在运行；若发生已能监测的断连/权限失效，可以看见并恢复，不必反复手动检查。

**最小范围**
1. 权限状态、真实服务连接、最后有效页面/通知事件及最近明确异常分开展示；
2. 能识别“已授权但未连接”“权限关闭”“部分采集来源异常”“状态未知”，并有清晰修复入口；
3. 检测到有证据的故障时以系统允许的方式提示；健康时安静，但状态可随时查看；
4. 恢复后状态更新，不把过期异常永久挂着；不因长期没有交易就报服务坏；
5. 已有健康功能先审计和复用，重点补 Android 真机证据与用户恢复体验。

**验收**
- 通过模拟/真机断连和权限撤销验证状态不误报；
- 真实连接恢复后界面随观察到的回调更新，留测试记录；通知权限关闭时 App 内仍可查看；
- 显示“采集服务连接正常”**不等于**“所有交易都已入账”；第三方根本不出通知时不能凭空监测。

**不做**：全自动对账、不受 Android 限制的“绝对实时故障推送”、AI 对话、大规模健康分析后台。

### v1.4.0｜外部 AI 经 MCP 可信使用个人财务数据（OM-05）

**用户确认的产品边界（D13 更正）**：清衡是自托管的个人财务数据和管理系统，提供授权的 MCP 工具供 ChatGPT、Claude 等外部 AI 客户端调用。**当前不做内置大模型、不做清衡内部 AI 聊天页、不承担自营模型推理和模型订阅费用。**用户以后若另定闭源上架、订阅制战略，才重新讨论是否内置 AI；不自动纳入本轮计划。

**核心用户任务**：用户在自己选择的外部 AI 客户端中，经授权读取清衡的数据，完成一个具体的财务查询/核对任务，结果有明确统计口径、时间范围和可追查的原始记录。

**不是从零开始的功能**：[MCP v1.2.0 兼容性与权限验收](MCP_V120_COMPATIBILITY.md) 记录清衡已有 18 个 MCP 工具（8 个只读、10 个授权写入），包括 `list_recent_transactions`、`spending_summary`、`personal_finance_long_term_trends`、`get_subscription_list` 等；OAuth/PKCE 与读写 scope 已有设计。因此本版先做**能力审计、数据契约补齐、外部客户端端到端验证**，不重复开发已有工具。文档中的工具清单代表仓库记录，正式开发前还需核对当前代码、部署和客户端发现结果。

**最小范围（MVP）**
1. 审核实际 MCP 工具清单、输入参数、输出契约与授权边界：哪些统计可直接调用，哪些信息需要提供交易明细以溯源；不足才新增或完善工具；
2. 选定一项真实任务，比如“统计最近 30 天实际支出，正确处理退款/排除的记录和内部转账，说明口径并找到相应交易”；注意存在多币种时须分别列示或明示换算依据，不允许无依据混加；
3. 用经核对的合成/脱敏账本建立预期答案。金额等确定性计算尽量由可信查询/统计接口完成，外部模型负责理解问题、选择工具和解释，不让语言模型自行编造数字；
4. 让至少一个支持 MCP 的外部 AI 客户端完成授权、工具发现、只读调用、回答与记录溯源的端到端任务；记录失败样本和异常行为；
5. 验证 OAuth 只读令牌无权调用写工具；已有写入能力仍需明确 finance:write 授权与逐次用户确认，不能因 AI 调用而默认自动修改真实账本；泄漏数据、权限越界属于发布阻断项；
6. 网络/工具不可用、时间范围内没有数据、来源不完整或证据不足时，应给出可理解的失败/数据缺口，不能伪装成完整财务结论。

**验收 / Go-No-go**
- 预先固定测试集、参照答案和排除规则；对真实发生的交易、退款和排除记录逐项验证，返回数据来源可追查；
- 至少一款外部 AI 客户端通过 OAuth 授权并真实完成一次可复现任务；检查权限拒绝、错误处理、缺失数据等反例；
- 与清衡网页或直接查询结果核对金额、币种、时间窗口与交易范围，无虚构记录或未经授权的写操作；
- 若现有 MCP 已能可靠完成任务，**本版可以以互操作性/契约验收作为成果**，不必为了版本号添加新的 AI 功能或工具；
- 不通过则缩小到一个工具/一个任务，修复契约和权限；仍无法安全可靠完成时不发布，不转而开发内置聊天页来掩盖问题。

**明确不做（Non-goals）**：清衡自带 AI 聊天界面、模型托管、模型付费/订阅、多轮 Agent 记忆、自动理财决策、未经用户确认的批量修改、真实支付操作、所有 MCP 客户端一次全支持。

**其他版本依赖**：v1.2.0 质量门禁不可跳过；v1.3.0 采集健康可见对线上数据可靠性有价值，但本版的**脱敏数据 MCP 实验无需等所有手机数据源完美采集**。

### v1.5.0｜成功反馈轻量可控（OM-02）

**核心任务**：用户能在不被每笔支付打断的前提下知道实际成功保存的交易，且自主决定是否提示。

**最小范围**
- 真正持久化成功后才可显示“成功”，显示有来源的金额/商户/时间；
- 简洁轻提示 + 开关；关闭成功提示不关闭权限异常或采集故障告警；
- 同一笔交易的多来源/重试/同步不重复弹成功；
- 对比开关使用情况、通知干扰、误提示与用户能否找到最近记录；遵守 Android 通知/后台弹窗限制。

**不做**：花哨动画、未经验证的强制每笔浮窗、替代故障诊断的“假成功”。

### v1.6.0｜账本异常可核对、可恢复（OM-01/04 完整用户体验）

**核心任务**：用户发现差异时能知道下一步做什么，修正后可重新核对，暂无法解决时不丢失线索。

**最小候选范围**
- 先辨别漏记、疑似重复、字段错误、跨设备未显示；模糊重复保留原始证据并让用户确认；
- 有可操作的修正、同步检查与待处理入口；退出与重进后保留状态；
- 结果以“账单差异实际解决”验收，不以“手动补录成功”当终点。

**前置安全说明**：任何涉及真实数据丢失、错误去重的缺陷都必须在发现当版优先修复；本版只安排**增强型用户操作体验**，不是允许之前版本带错误入账上线。

## 3. 一版一目标：工作方式

1. **进入某版本前**：检查上版发布/真机证据、未完成缺陷和真实用户反馈；明确 1 个核心目标、2–5 个可验收交付项。
2. **需求分层**：Must 保证该目标可验收；Should 改善关键体验；Could 资源富余再做；Won't 明确本轮不做。工程安全门禁在所有版本优先于 RICE。
3. **基线与数据保护**：先记录当前 Git SHA、数据库备份/签名/回滚方案；变更通过独立 PR 或审阅留痕。
4. **实现**：先最小工作项、真实失败样本与测试；不要为“看起来 AI”堆砌功能。
5. **验收**：单位测试、集成/真机验证、关键用户任务和发布签名，保留通过/失败/阻断证据。
6. **发布与复盘**：发布完成才改状态；记录新证据、用户体验与下一版机会池，不以代码合并代替发布完成。

**版次规则**：`v1.x.0` 代表新的用户价值里程碑；`v1.x.y` 用于修复已知问题和提高兼容性；RC / beta 必须独立标注预发布，不能冒充 GA。发布前再次核对版本号、tag、后端/Android 兼容和签名/迁移方案。

## 4. 仍需要和产品负责人进一步讨论的三个取舍

1. **v1.2.0 正式发布门禁**：是否决定先逐项完成真机、升级、备份/恢复，再正式进入 v1.3.0？建议 **是**。
