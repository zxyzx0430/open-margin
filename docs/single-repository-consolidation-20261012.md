# 个人财务系统：双仓库合并为唯一公开代码源

状态：已检查仓库现状；不直接改变生产运行目录或仓库可见性。本文件是合并实施清单。

## 目标

- **唯一代码源：** `zxyzx0430/open-margin`，未来所有 Android、Finance API、Wallos 扩展、文档与测试的代码只提交到这里。
- **运行环境：** VPS 从这一个仓库的确定提交部署。真实数据和机器专有配置始终保存在仓库以外，不能纳入公共 Git 历史。
- **历史仓库：** `personal-finance-system` 保留私有归档、历史问题记录与紧急回滚用途；切换完成后不再向它提交业务代码；不把其历史合并到公开仓库。
- **数据库：** Wallos 订阅数据库和 Finance 交易数据库继续彼此独立。此处只合并 Git 仓库，不合并两种不同职责的数据库。

## 2026-10-12 的实际差异审计

生产私有仓库跟踪 183 个文件，OSS 仓库 180 个文件。22 个文件只在私有版出现、19 个只在 OSS 出现、26 个同路径文件内容不同。这并非仅仓库名称不同。

主要区别：

1. 私有版包含当前 systemd 服务、VPS Nginx 配置和独立安装脚本；安装脚本硬编码 `<deployment-root>/project`。它们属于部署适配层，公开版需要用可配置路径和脱敏模板替换，不能将机器特定实例参数原样发布。
2. 私有版 FastAPI 为 v1.5.0，包含 `backend/v15_reconciliation.py` 与相关导入、复核 API；公开版仍为 v1.4.1 且不包含这些接口。必须核对保留、迁移或正式退役，不能强行降级替换运行中的 API。
3. 公开版有 `backend/config.py` 的环境参数化、单用户边界控制、`compose.yaml`、Dockerfile、首次安装脚本、公开版安全和第三方许可文档；这些比私有版硬编码更适合做主线。
4. 公共与私有代码在 OAuth、MCP、Wallos 路由、账单入口和交易筛选方面也有实际实现差异，必须按功能测试逐项合并。生产数据已发生、即将到期未支付等财务口径绝不能发生回退。
5. 私有版还有若干测试截图/验收报告，公共版另有 CI 和安装文档。图片与文档应检查是否含私人凭证、实际消费明细、账号或可识别的环境信息后再决定是否迁移。

## 合并实施顺序

### M0. 锁定唯一来源与单仓库约束

- 以 OSS `main` 为基础建立 `unify/single-source` 分支，而不是做两个仓库的历史合并。
- 把原私有部署脚本的通用逻辑参数化迁移到公开仓库：配置从环境变量和 VPS 私有文件读取；不得含私人域名、令牌、数据库或真实财务内容。
- 把发布脚本统一为读取一个工作树，取消每次 UI 修改都要复制到两个仓库的流程。

### M1. 后端功能并轨

- 逐项比较私有版与 OSS 版的 HTTP 路由和 MCP 注册工具。对新增功能补端到端测试。
- 对早已撤销的订阅与扣款对账 UI，要明确处理私有版剩余的 v1.5 API：兼容期保持原有数据表，不可悄悄删实际交易或删掉正在使用的 API。
- OSS 原有的可配置 OAuth 域名、Wallos owner 身份校验和部署配置作为统一实现基线，避免反向覆盖。
- 真正执行切换前，使用脱敏测试数据库和生产数据库的一次只读快照跑兼容性回归。

### M2. 部署目录与生产服务切换

- 新唯一代码目录建议 `<deployment-root>/app`（来自 OSS 唯一仓库）。
- 预先复制并保留当前 systemd/Nginx 配置与容器镜像；以精确 Git commit 和产物哈希部署。
- 先在隔离端口验证新 API、Wallos 登录、Android 上传协议、OAuth/MCP、支付记录排除、预算及订阅汇率；通过后再将 `finance-api.service` 的 `WorkingDirectory` 指向统一代码。
- Wallos 使用同一工作树构建，数据库继续复用现有宿主机卷。禁止为合并而重新初始化数据库。
- 如有异常，将服务路径及 Wallos 旧容器恢复；不能通过删除数据库修复。
- 验收覆盖移动端 320/390px、桌面端 768/1440px、亮暗主题、数据一致性与原有 24/24 页面测试。

### M3. 单仓库维护

- GitHub 的 OSS `main` 成为唯一活跃分支；停止双提交和双发布。
- 给公开仓库配置自动单测、前端语法、PHP 验证、敏感数据扫描、独立干净安装的 CI 关卡。
- 将旧私有仓库仅保留为只读历史/回滚档案，**不要**改变它的可见性，因为旧 Git 历史仍需审查。

## 本次评估的结论

**可以合并，而且值得合并。** 但必须以公开 OSS 代码为唯一主线做功能并轨，处理后端 v1.4.1 / v1.5.0、权限与部署路径差异后才能安全切换 VPS。简单把私有仓库设成公开、覆盖 OSS 源码或直接复制整棵工作树都不合格。
